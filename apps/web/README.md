# PvP Referee web

Next.js 15 App Router UI. From the repository root run `pnpm dev:web` or `pnpm --filter @pvp/web build` / `start`. Node 22 scripts load `../../.env` with `--env-file-if-exists`; tests never load it. Next 15.5.28 is pinned to the latest 15.x patch reported by npm on 2026-10-28 ([official October advisory](https://nextjs.org/blog/nextjs-security-update-october-14-2026)). React 19.3.1 satisfies Next's React 19 peer range.

## Request flow

- `/` starts with two separate contract-address inputs and supports 2–10 boxes. It submits repeated `ca` fields, each containing one 32-byte Solana public key; the server rejects mixed legacy/new fields, blank or multi-address rows and more than ten boxes. Duplicates still count once. The checker does not need to find or supply a meme source.
- `/resolve` automatically calls `discoverOrigin` when no source hint is present: it looks up exact base-mint links through the public DexScreener API and bounded explicit source references, then uses the existing independent source-authority/audited-review checks. Token websites/social claims are discovery leads, not canonical facts. A research trail explains candidates and incomplete/conflicting evidence. No general web-wide or semantic origin search is claimed.
- Existing `cas`/`source_url` bot and review links remain supported. A source hint is optional recovery after unsuccessful automatic research. `createSourceFromEnv()` runs independently of Helius; automatic source fetches use a four-second, 1 MiB transport bound. If a database is configured, a stored audited override takes precedence. A failed audited lookup never falls back to unaudited facts. Missing or conflicting sources block the ruling; discovery does not perform historical ingest.
- The issue action accepts only addresses, an optional source hint, version, and a review fingerprint. It independently repeats discovery/resolution, including saved reviews. A changed fingerprint requires another review. The hash detects changes, **not authorization**. Client meme objects, canonical edits, endorsements, actor/auth flags, duplicate singleton fields and unrecognized fields are rejected. Verified endorsements from the server resolution are passed to `pipeline.runResolved` unchanged.
- The pipeline owns fact collection, scoring, and immutable persistence. The action redirects only after persistence succeeds. `/ruling/[slug]` reads the saved payload from the repository, with no re-scoring, provider lookup or Helius requirement.
- `/rulebook` renders the committed live config without provider credentials. Stored rulings display their frozen config instead of loading today's version.
- `/api/card/[slug]` calls the agreed `@pvp/card` export lazily and serves an immutable PNG. Missing rulings return 404; repository/renderer failures return a sanitized, uncacheable 503. The UI handles image failure and still permits permalink sharing. Tests inject a renderer; they never invoke the CARD scaffold.

Database pools/runtime resources are request-scoped and closed in `finally`. There are no connections or credential checks at module import. Root and rulebook are statically renderable. No remote fonts, source images, or demo/live evidence are fetched at build time. The web host pins sharp 0.35.5 and resvg 2.6.2 and explicitly externalizes their native bindings. Native dependencies and the card package's `assets/` and `fonts/` folders are traced for standalone builds; embedded fonts require no runtime file paths. Workspace `.js` import specifiers resolve to TypeScript through webpack's extension aliases.

## Administrator and operations

`/admin/login` authenticates the single configured administrator using `ADMIN_PASSWORD_HASH` and HMAC sessions. From an automatic research trail, open a specific source to review it: an empty automatic lookup URL cannot create an override. `/resolve` renders the editable review form only for that session and concrete source. Source writes load the current baseline on the server, reject stale review fingerprints, and call the source audit service and repository's transactional `applyMemeOverride`. Auth requires fixed `SOURCE_ADMIN_ACTOR`, `ADMIN_EMAIL`, `SESSION_SECRET` and `APP_ORIGIN`; `ADMIN_PASSWORD` is not used. Public resolution still requires no Helius credential.

`/admin/rerun` saves a new ruling and grid diff from frozen facts under a selected committed config. Buyer-count/window changes require fresh ingest. Compatible snapshots retain their exact original envelopes in derivation provenance; no observed-cache entries are rewritten. The static config registry preserves all published versions and v1's exact hash.

Comparison/source/card/admin/login entrypoints have server-side budgets. Production requires shared Redis REST and fails closed without it; memory is development/test only. Unverified forwarding headers never identify clients. See [the operations runbook](../../docs/runbook.md) for session setup, CSRF/origin requirements, signed ingress identity, budget semantics, key rotation, environment additions and compatible historical re-evaluation.

`pnpm --filter @pvp/web start` copies static assets into the generated monorepo standalone directory and starts its `server.js`; it does not use unsupported `next start`. `cache:warm` is a single-run command with an explicit unsupported default until a reviewed trending/ledger adapter is installed. It warms only one exact UTC checkpoint per selected mint, with Postgres read-back verification, not arbitrary rival times.

## Verification

`pnpm --filter @pvp/web test`, `typecheck`, and `lint` cover inputs, server actions, authenticated gates, CSRF, rate-limit failures, stale reviews, concurrent creation, arbitrary-field rejection, field audits, immutable reruns, snapshot provenance, provider/repository lifecycle, source override precedence, safe evidence rendering, frozen thresholds, warming failures and mocked card responses. Tests use synthetic fixtures and the root network/DNS/socket denial setup. No live source claim or local Postgres smoke row is used.

Warm-cache latency under 15 seconds is a target, not a measurement from this implementation. Source resolution is deliberately repeated at submission, cold reconstruction may take longer, and upstream ledger/provider capabilities determine whether a complete ruling is possible. Live provider, Redis and production validation require configured operational services.
